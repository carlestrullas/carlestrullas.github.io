Deploy code ML architecture on Databricks

One repository, three environments, and a pipeline where a pull request validates and a merge deploys. This is how I structure a machine-learning project on Databricks so that it reaches production in a reliable, repeatable way.

  • Databricks
  • MLOps
  • Asset Bundles
  • CI/CD
  • MLflow

Training a model is the easy part. The hard part starts the day it has to run every week, on real data, without anyone copying files by hand. Without a clear structure, the same problems always appear: models moved manually between environments, jobs created by clicking in the interface, "it worked in my environment", and nobody sure which version is running in production.

This post describes the architecture we used in a machine-learning project on Databricks. It is not about one specific model. It is about how to organise the repository, the environments and the deployment so that the path to production is reliable and repeatable.

The setup this post assumes

Before anything else, it helps to be clear about the starting point. Everything in this post assumes that you work with three separate Databricks environments: development, QA and production. Each one is its own workspace, and each one has its own data.

The data does not start equal in the three. Production holds the real data: it is the one that the business uses and it is updated every day. From time to time, that data is copied to QA and to dev, so that there is realistic data to work with there too.

Not every company works like this. Some have a single Databricks workspace for everything, and then part of what follows does not apply directly. But if you have separate environments, or plan to have them, this is a structure that makes good use of them.

Two ways to ship a model

Imagine you have trained a model that forecasts weekly orders. It works well in the development workspace. Now it has to reach production. What exactly do you move there?

There are two common answers to that question.

The first is deploy model. You train the model once, in development, and then copy the trained model to QA and to production. It is simple, and the model you tested is exactly the model that runs.

But this pattern has a condition. To train a good model in development, the development workspace has to read production data. In many companies that is not allowed, for security or privacy reasons.

And there is a second problem: retraining. Every new model has to be trained in dev and then promoted again, which makes automatic weekly retraining hard.

The second answer is deploy code. Instead of moving the model, you move the code that trains it. Each environment runs the same training code on its own data, and produces its own model.

Deploy code is not a Databricks feature. It is a general way of working in MLOps, and you can apply it on any platform. This post shows how we applied it on Databricks.

Why we chose deploy code

Our model has to learn from the newest real data, and that data lives in production. With deploy code, the production model is trained in production, with production data. The development workspace never needs direct access to production data, and no model trained on that data ever leaves the production workspace.

Retraining also becomes simple. The training job runs on a schedule in production, so a new model appears every week without anyone training it by hand or copying a model file from one place to another.

There is one more benefit, and it is easy to miss. With deploy code, the thing you test in dev and QA is the training code itself. By the time that code reaches production, it has already run successfully twice, in two different environments. If something is wrong with it, you usually find out before production does.

Deploy model is not a bad choice. If training takes days, if a model must be approved once and then never change, or if everything runs in a single workspace, it is often the better option. The right pattern depends on your project.

In short, this is the trade-off:

What you gain

  • The production model learns from production data, and dev never needs direct access to it.
  • Automatic retraining is simple: it is just a scheduled job.
  • The training code reaches production already tested in dev and QA.
  • Everything comes from Git: reviewed, versioned and repeatable.
  • Models trained on production data never leave production.

What it costs

  • You train in every environment, so you pay for more compute.
  • Dev and QA need data that looks like production data.

Three environments, three branches

If the code is what moves between environments, we need a clear answer to a simple question: which version of the code runs where?

Without a rule, this gets messy fast. Someone deploys a half-finished change to QA to test it. Production runs a version that nobody can find in Git. Two people overwrite each other's work in the same workspace.

Our rule removes that doubt: each workspace runs the code of one Git branch. Dev runs develop, QA runs qa and production runs main. If you want to know what is running in production, you look at main. Nothing else.

Apart from the code, nothing is shared. Each environment has its own data catalogs, its own jobs, its own MLflow experiments and its own registered models. If something breaks in dev, production does not notice.

This also makes moving a change forward very simple. To take code from dev to QA, you merge it from develop into qa. To take it to production, you merge it into main. Moving code between environments becomes the same thing as moving it between branches.

One repository, and what each piece is for

Everything lives in a single repository: the training code, the job definitions, the tests and the pipeline. That matters more than it seems. A change to the training code and a change to the job that runs it travel together, in the same pull request, and are reviewed together.

The layout is small, and each piece has one job.

my-ml-project/
├─ databricks.yml        # the central file: what is deployed, and where
├─ resources/jobs/*.yml   # Databricks jobs, defined as YAML
├─ src/                  # the code the jobs run: training, inference…
├─ tests/                # automated tests that protect every change
└─ cicd/pipeline.yml     # CI/CD: connects Git with Databricks

If you understand what these five pieces do, you understand the architecture. The rest of this post goes through them.

databricks.yml: what is deployed, and where

Now think about what a deployment to one workspace actually involves. You need to upload the training and inference code. You need to create the jobs that run it, with the right cluster and the right schedule. And all of that must point to the data of that environment, not another one.

Doing this by hand, three times, for every change, is slow and easy to get wrong. One wrong click and the QA job reads production data, or production runs an old notebook.

This is the problem that Databricks Asset Bundles solve (the documentation now calls them Declarative Automation Bundles). A bundle packages your code and your job definitions as one unit that you can deploy. You describe once what must exist, and the bundle creates it in whichever workspace you choose.

The file databricks.yml is the entry point of the bundle. A simplified version looks like this:

databricks.yml 
bundle:
  name: my-ml-project

include:
  - resources/jobs/*.yml

variables:
  environment:
    description: name of the environment
  cluster_id:
    description: compute for the jobs
  catalog:
    description: data catalog of the environment
  training_cron:
    description: training schedule
    default: "0 0 6 1 * ?"        # first day of every month

targets:
  personal:
    mode: development
  dev: {}
  qa: {}
  prod:
    variables:
      training_cron: "0 0 6 ? * MON"  # every Monday

It has three parts:

  • The bundle: its name and which resource files it includes.
  • The variables: everything that changes from one environment to another, such as the cluster, the data catalog or the schedule.
  • The targets: one destination per environment. A target can override variables. In this example, dev and QA retrain once a month, which is enough to check that the code works. Production overrides the schedule and retrains every Monday, because that is where fresh data matters.

The same bundle is deployed to any target with a single command:

databricks bundle deploy -t <target>

Notice that the variables have no values for the cluster or the catalog. The real hosts, cluster IDs and catalog names are not in this file. The pipeline passes them in at deployment time, so the repository holds no environment-specific values and no credentials.

Jobs are code too

The jobs are not created by hand in the Databricks interface. They are YAML files in resources/. This is a simplified training job:

resources/jobs/training.yml 
resources:
  jobs:
    train_pipeline:
      name: Training pipeline ${var.environment}
      schedule:
        quartz_cron_expression: ${var.training_cron}
        timezone_id: Europe/Madrid
      parameters:
        - name: catalog
          default: ${var.catalog}
      tasks:
        - task_key: train_model
          existing_cluster_id: ${var.cluster_id}
          notebook_task:
            notebook_path: ../../src/training/train_pipeline.py

Nothing is fixed. The name, the schedule, the cluster and the data catalog all come from the bundle variables. So one definition creates the same job in every environment, and in each one it points to the data of that environment.

In the Databricks interface, a job deployed this way shows a notice saying that it comes from a bundle. That is the correct behaviour: if you want to change the job, you change the repository, not the interface.

One note on compute. To keep the example short, the job runs on an existing cluster. For scheduled jobs, a job cluster or serverless compute is usually the better choice: it only exists while the job runs, so you do not pay for a cluster that sits idle.

CI/CD: the pull request validates, the merge deploys

The bundle tells Databricks what to deploy. But someone still has to run the deploy command, at the right moment and for the right target. If that someone is a person, the old mistakes come back: the wrong target, a forgotten step, a deploy from a branch that was never reviewed.

That is the job of the CI/CD pipeline. It is one more YAML file in the repository. We used Azure DevOps, but the idea is the same in GitHub Actions or any other tool. It defines when the pipeline runs and what it does in each case.

cicd/pipeline.yml 
pr:                # runs on pull requests to these branches
  branches: [develop, qa, main]

trigger:           # runs on merges to these branches
  branches: [develop, qa, main]

stages:
  - Validate       # tests + bundle validate
  - Deploy_DEV     # only on develop
  - Deploy_QA      # only on qa
  - Deploy_PROD    # only on main

When you open a pull request, the pipeline runs the automated tests, scans the dependencies for known vulnerabilities and runs databricks bundle validate. Nothing is deployed. When the pull request is merged, the pipeline deploys the bundle to the environment of that branch.

One detail if your code lives in Azure Repos, as ours did. There, the pr: block in the YAML is ignored. Pull request validation is set up with a branch policy instead: on each protected branch (develop, qa and main), you add a build validation rule that runs this pipeline. The YAML above keeps the pr: block because it shows the idea clearly, and it works as written when the repository is on GitHub.

The result is that nobody deploys by hand to the shared environments. If the code is in main, it is in production. If it is not, it is not.

How we develop

There is one problem left. Before merging a change, you want to try it in Databricks, with real jobs and real data. But the dev workspace is shared: if everyone deployed over the same jobs, people would overwrite each other's work all day.

Every change starts in its own branch, created from develop: a feature/, a fix/ or a bugfix/. Before merging anything, you can deploy the whole bundle under your own name with the personal target.

databricks bundle deploy -t personal    # deploy your own copy
databricks bundle destroy -t personal   # remove it when you finish

The personal target uses mode: development, and you deploy it with your own user. Together, that gives you three useful things:

  • Because you deploy it yourself, the files go to your own user folder in the dev workspace, not to the shared one.
  • Development mode adds your user name as a prefix to the jobs, so they do not replace the jobs of the team.
  • Development mode also pauses the schedules. Your copy only runs when you start it.

Your personal deployment uses the development data, so you test the change in real conditions. When it works, you open a pull request to develop: the tests run, a teammate reviews it, and it is merged.

Promotion to QA and production

At this point the change is in develop, and the pipeline has deployed it to the dev workspace. But develop keeps moving: other people merge their own changes there every day. So it is not a good place to decide what goes to production.

That is why we use a release branch. When we want to publish a new version, we cut a branch such as release/1.4.0 from develop. This freezes a set of changes. New work can continue in develop without touching the release.

The release then moves forward in two steps:

  1. A pull request takes the release into qa. When it is merged, the pipeline deploys it to the QA workspace. There, the team checks that the training job runs, that the model is good enough and that the results make sense.
  2. If QA approves it, a second pull request takes the same release into main. The pipeline deploys it to production and creates a version tag in Git, such as v1.4.0.

If QA finds a problem, the fix goes into the release branch itself, not into develop. And once the release reaches main, it is merged back into develop, so those fixes are not lost in the next release.

The tag is a small detail with a big benefit. Months later, if someone asks which code trained the production model, the answer is one Git tag away.

What happens inside each environment

So far we have talked about how code moves. Now let's look at what that code does once it arrives. After the deployment, each environment has a training job and an inference job. From here, the life of a model is the same everywhere:

  1. The training job runs on a schedule, with the data of that environment.
  2. Every run is logged in the environment's MLflow: parameters, metrics and artifacts.
  3. The trained model is registered as a new version in the environment's model registry, in Unity Catalog.
  4. If the new version passes a quality check, it receives the alias champion. The check can be a minimum score, or, more often, being at least as good as the current champion.
  5. The inference job does not know about version numbers. It always loads the champion: models:/<catalog>.<schema>.<model>@champion.

The alias deserves a closer look, because it solves a real problem.

In production, the training job creates a new model version every week: v30, then v31, then v32. If the inference job pointed to a fixed number, someone would have to change the code and deploy again every time a new version appeared. And if a new version turned out to be worse, nothing would stop it from being used.

An alias is a name that points to one version, and that you can move. The inference job only knows the name champion. It does not care which number is behind it.

  • If the new version passes the quality check, the alias moves to it, and the next inference run uses it.
  • If it does not pass, the alias stays where it was, and inference keeps using the previous model.
  • If a problem appears later, you move the alias back to an older version. That is your rollback.

In all three cases there are no code changes and no new deployment. The decision about which model to use lives in the registry, not in the code.

Each environment, its own model

This is repeated, in the same way, in the three environments. Each one has its own MLflow and its own version history.

EnvironmentCode fromExperimentsModel versions
DEVdevelopMLflow in devv11, v12 @champion
QAqaMLflow in QAv4, v5 @champion
PRODmainMLflow in prodv30, v31 @champion

Version 12 in dev has nothing to do with version 31 in production. They were trained by the same code, but on different data and at different times. The production model was trained in production, with production data. Between environments, only the code moves.

The whole picture

We have looked at the pieces one by one. Here they are together. Read it from top to bottom: Git decides which code each environment runs, the pipeline deploys it, and inside each workspace the same chain repeats with its own data, its own MLflow and its own model.

Six ideas to take away

  1. Deploy code: promote the code, not the model.
  2. Three environments, three branches: develop, qa and main.
  3. databricks.yml defines what is deployed, and where.
  4. CI/CD: the pull request validates, the merge deploys.
  5. Each environment trains and versions its own model.
  6. Develop in your own branch, with a personal deployment.

None of these pieces is complicated on its own. The value is in how they fit together: once the structure exists, taking a change to production is opening a pull request.
